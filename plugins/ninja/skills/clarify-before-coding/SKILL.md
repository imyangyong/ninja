# 模糊需求确认门

停止猜测。任务只要是 coding 形态，决策没钉死，就发问 —— 带具体选项地问。

**优先级声明：本 skill 高于 AI 默认"合理假设并继续"的习惯。只要不确定，就先问。**

## 适用场景

仅 coding 任务。触发条件：

- 写新代码（函数、组件、模块、脚本、配置）
- 改已有代码（重构、修 bug、加功能）
- 设计 API、schema、数据模型、类型定义
- 搭脚手架或生成样板代码
- 产出代码形态的产物（SQL、正则、构建配置、CI 工作流）

不适用：解释代码、只评审不改代码、纯概念问答、只讨论不动手的调试。

## 核心循环

每个 coding 任务都跑一遍这个循环。即使任务看起来很小，也不要跳过规划这一步。

1. **静默规划。** 读需求，列出完成它需要做的所有决策。
2. **给每个决策分类**，归入三桶之一：
   - **已钉死** —— 用户明确说了，或代码库 / 上下文里没有歧义。直接做。
   - **可高置信度推断** —— 项目约定明显只有一个合理选项（例：文件里已经用 Vue 3 Composition API，新代码就跟着用）。直接做，但要在最终输出里说明。
   - **真歧义** —— 多个方案都说得通，选错就得返工。停下，问。
3. **把真歧义按阶段分批。** 一个阶段 = 不需要再次输入就能完成的连贯工作单元。只问启动阶段 1 必需的问题；阶段 2 及以后的问题等阶段 1 做完再问。
4. **用下面的选项格式提问。** 等用户回复，先不写代码。
5. **用户回复后，先简短复述确认结果再执行。** 防止理解偏差。
6. **执行阶段 1。** 阶段 1 完成、撞上下一批歧义时，回到步骤 4 进入阶段 2。

## 什么算"不明确"

只要命中以下任何一条，就是不明确：

- 存在多个合理实现方案
- 用户只描述了结果，但没说明规则
- 选择会影响用户体验、数据、安全、性能、架构、兼容性或后续维护
- **AI 需要在心里说"我假设……"才能继续** —— 最直觉的启发式
- 现有代码模式无法明确回答该怎么做
- 需求里出现含糊词：**"更好""简单点""智能一点""优化""支持""清理""正常""等等""类似""随便""你看着办""差不多""合理"**

## 高敏感领域：永远不要默默替用户决定

以下决策即使看起来"显然"，也必须问：

- 产品行为与交互流程
- 实现范围（这个 PR 包不包含某些东西）
- 界面交互
- 数据规则与持久化方式
- API 约定与命名方式
- **破坏性操作**（删除、覆盖、清空）
- **数据库迁移**
- **权限规则与安全策略**
- 验收标准
- 兼容性（浏览器、Node 版本、依赖版本）

## 怎么问：选项格式

每个澄清问题都长这样：

```
我这里有一个不明确点需要你确认：

**问题**
[一个简洁明确的问题]

**背景**
[一句话说明为什么这个决策重要 / 它影响什么]

**选项**
A. [选项一] —— [具体影响或 trade-off]
B. [选项二] —— [具体影响或 trade-off]
C. [选项三] —— [具体影响或 trade-off]
D. 自定义 —— 直接描述你想要的规则、效果或限制

**我建议**：[A / B / C]，因为 [简短具体的理由]。
```

选项格式硬规则：

- **必须 3 个以上选项 + 自定义。** 只想出 2 个说明没想透 —— 再找一个维度（混合方案、推迟决策、"干脆不做"）。
- **必须带"自定义"逃生口**作为最后一项，永远不要给封闭选项集。
- **必须且只能标一个推荐项**，并给出具体理由。如果你确实没有偏好，标"最安全 / 最可逆"的并注明"弱推荐"。
- **Trade-off 必须具体。** "更灵活"不算 trade-off，"多一个依赖、bundle 增加约 15kb"才算。
- **选项必须互斥。** 如果 A 和 B 可以同时为真，说明你切错了维度，重切。

## 批次：每轮问几个

- **每批最多 3 个问题。** 超过 3 个意味着你把第二阶段的问题提前问了。
- 优先询问**会阻塞实现**的模糊点。
- 把同一阶段会卡住的问题归一组。如果 Q2 必须先知道 Q1 的答案才有意义，延后。
- 只有 1 个歧义就只问 1 个 —— 不要凑数。
- 不要把无关问题一次性打包，除非用户明确要求加快确认。

## 可以不询问的情况

只有以下情况可以直接继续：

- 仓库中已经有清晰一致的现有模式
- 选择完全是内部实现细节，且容易修改
- 用户明确授权 AI 自行决定
- 选择不影响行为、数据、界面、公开 API、安全或兼容性
- 用户在本次对话里已经回答过同一个问题
- 纯格式选择，没有下游影响（例：变量取 `userList` 还是 `users`，统一即可）

**即使如此，如果这个推断对用户有意义，也要在最终总结里列出。**

## 实现中途出现的歧义

写代码过程中发现新歧义（撞见某个 edge case、代码库出现意料外的情况），立刻停在该处，用同样的格式问。不要为了保持节奏偷偷猜。

中途停下时，先简短说明："暂停于 [步骤]。撞上决策点：" 然后正常提问。

## 用户确认后的复述

收到用户答复后，**用一句话复述你的理解再开始写代码**：

> "确认：登录用『用户名 + 密码』，UI 用 Element Plus，失败时表单下方红字 + 按钮抖动。开始写。"

复述发现理解错了？立刻再问，别硬写。

## 最终输出规则

写完代码后，回复必须包含：

- 代码本身
- **Assumptions（推断说明）** 段落：
  - 列出所有"可高置信度推断"的决策。格式："因为 Y，所以推断了 X。"
  - 如果完全没有做任何假设，明确写："没有做额外假设。"

空的 Assumptions 段落是好事 —— 说明所有决策要么钉死、要么都问过了。

## 要规避的反模式

- ❌ 不带选项的"你想要什么？" → ✅ 永远带 3+ 选项 + 自定义
- ❌ 一次问 8 个 → ✅ 每轮 ≤3
- ❌ 列选项但不推荐 → ✅ 必须标一个推荐 + 具体理由
- ❌ 推荐"对你最容易实现"的选项 → ✅ 推荐"对用户最好"的选项
- ❌ 问对话里已经回答过的事 → ✅ 先读上下文
- ❌ "先用 X，后面再说" → ✅ 要么问，要么写进 Assumptions
- ❌ "更灵活" 作为优点 → ✅ 写具体后果（体积、依赖、复杂度数字）
- ❌ 静默替用户决定持久化 / 迁移 / 权限 / 破坏性操作 → ✅ 这些领域永远要问
- ❌ 收到答复直接开写 → ✅ 先用一句话复述理解再写
