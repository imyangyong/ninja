# 优化存量代码

优化**已经实现好**的代码：先分析、出清单，用户确认后再动手。与 `code-review` 的边界：它评审增量 diff、对照需求，是合并前门禁；本 skill 改进存量代码，不管 git 历史，是主动的质量进化。

## 阶段一：分析

对用户指定的范围（函数、文件、模块），按六个角度逐一扫描。范围小于模块时裁剪不适用的角度。

1. **正确性与边界**——空值、异常路径、并发/时序、边界条件。
2. **代码异味与设计**——按 Fowler 异味目录（Mysterious Name、Duplicated Code、Feature Envy、Data Clumps、Speculative Generality、Middle Man 等）扫描，并检查模块深浅、接口是否泄漏实现细节。**REQUIRED SUB-SKILL:** codebase-design
3. **一致性与约定**——对照仓库的 standards 文档（`CODING_STANDARDS.md`、`CONTRIBUTING.md` 等）和既有写法、既有工具函数。
4. **错误处理与可观测性**——吞掉的异常、缺失的日志与上下文。
5. **性能**——只报有实据的浪费（N+1、重复计算、不必要的拷贝/渲染），不搞臆测优化。
6. **可测试性**——难 mock 的依赖、隐藏的全局状态。

每条发现必须核实证据（引用具体位置），标注：角度、行为是否变化、有无测试保护。无测试保护的条目标注 ⚠️。

## 报告格式

按三档分级输出，结尾等待用户圈选（回复编号或"全做"）后才进入阶段二：

```text
## 优化分析：<范围>

共发现 N 项（阻断 x / 建议 y / 可选 z）

### 阻断（正确性问题，建议必改）
1. [正确性] `foo.ts:42` — 问题描述
   依据：<证据> ｜ 行为变化：是 ｜ 测试保护：有

### 建议（明确收益，低风险）
2. [异味] `bar.ts:10-35` — Duplicated Code：……
   依据：<证据> ｜ 行为变化：否 ｜ 测试保护：无 ⚠️

### 可选（判断性较强，可不改）
3. [设计] ……
```

## 阶段二：执行

若已安装 skill `yong-coding-preferences` 则加载并应用其偏好；未安装则跳过，照常执行。

对用户确认的条目：

1. 逐条修改；每条改完运行与该改动相关的检查（该文件的测试、类型检查、lint），通过后再改下一条。
2. 除"行为变化：是"的正确性修复外，所有改动必须保持行为不变；相关检查失败时回滚该条，报告并继续下一条。
3. 全部改完后跑一次范围级验证（所在包的完整测试与类型检查）。
4. 汇报：逐条列出"改了什么 / 验证结果"，以及被回滚或未做的条目。
