# 任务:Code Review
### 审查原则
1. **只报告真实问题**——每条必须指向具体文件:行号，基于实际代码而非"理论上可能"
2. **先森林后树木**——先看架构与设计是否合理，再看实现细节
3. **校准严重程度**——不是所有问题都是必须修复。把 **nitpick** 标成 🔴 会让实施者忽视真正的红色问题
4. **承认做得好的部分**——准确的称赞能让实施者信任后续反馈
5. **可执行的建议**——指出问题必须附带改进方案

### 审查维度
**维度零:Plan Alignment(仅在提供需求/计划时审查)**
- 实现是否匹配需求？所有计划的功能是否齐全？
- 偏离是有依据的改进，还是问题性偏差？
- 如果偏离了，**明确指出**让实施者确认是否有意为之
- 如果发现是**计划本身**的问题（而非实现的问题），明确说出来

**维度一:正确性与健壮性(最高优先级)**
- **空值边界**：`null`/`undefined`/空数组/空对象的防御性处理
- **异步安全**：`async/await` 是否有 `try/catch`；竞态条件（组件卸载后回调仍执行、过期请求覆盖最新数据）；用 `AbortController` 而非仅 `clearTimeout`
- **条件完整性**：`if/else` 分支是否覆盖所有情况；`switch` 是否有 `default`
- **隐式转换**：`==` vs `===`；`0`/`’’`/`false` 在业务语义中是否被错当成 `falsy`

**维度二:TypeScript 类型安全**
* 类型逃逸:`any`、`as unknown as X`、`@ts-ignore` 是否合理(必须有注释说明原因)
* 类型完整性:函数参数、返回值、响应式变量是否有明确类型
* 类型复用:是否使用工具类型(`Partial`、`Pick`、`Omit`、`Record`、`Awaited`、`ReturnType` 等)
* API 响应类型:接口返回是否有类型定义,而非当作 `any`

**维度三: 架构与组件设计**
- **职责分离**：组件/composable/store 的边界是否清晰
- **状态归属**：仅组件内部使用的状态是否被错误地放进了全局 store
- **Props 设计**：是否有合理的类型约束和默认值；子组件是否直接修改了 props
- **组件粒度**：单个组件 >300 行是否应拆分；单个函数 >50 行是否职责过多
- **集成性**：是否与周边代码风格一致

**维度三:性能**
- **不必要的重新计算/渲染**：是否该用 `computed` 而非模板内联表达式；`watch` vs `watchEffect` 是否选对
- **资源泄漏**：定时器、事件监听、订阅是否在 `onUnmounted` 清理
- **网络请求**：搜索/输入是否防抖；列表是否分页/虚拟滚动；过期请求是否用 `AbortController` 取消

**维度五:测试质量**
> 仅当变更涉及测试或应当涉及测试时审查
- 测试是否验证**真实行为**而非 mock 自身?
- 边界用例是否覆盖(空数据、错误响应、加载中、超时)?
- 单元测试和 E2E 各自的职责是否清晰,有没有重复或缺失?
- 异步逻辑的测试是否会有时序漏洞(`waitFor` vs 固定 `setTimeout`)?
- 所有断言是否都会真正失败?(避免 `expect(true).toBe(true)` 这种空断言)

**维度六:安全性**
- XSS:`v-html` 是否使用了未经过滤的用户输入;动态 `href/src` 是否有 URL 校验(防 `javascript:`)
- 敏感信息:token、密钥、内部 API 地址是否硬编码或被打包到产物
- 权限校验:前端路由守卫和接口鉴权是否完整(前端校验只是 UX,服务端鉴权才是安全)
- 依赖安全:新增依赖是否来自可信源,是否考虑供应链攻击风险

**维度七:命名规范**
| **类别** | **风格** | **正确示例** | **错误示例** |
|:-:|:-:|:-:|:-:|
| 局部变量 / 函数参数 | camelCase | orderList、pageSize | order_list、OrderList |
| 函数 / 方法 | camelCase,动词开头 | fetchUserList、handleSubmit | userData、submit |
| 布尔变量 | is/has/can/should 前缀 | isVisible、hasPermission | visible、flag |
| 常量 | UPPER_SNAKE_CASE | MAX_RETRY_COUNT | maxRetryCount |
| 组件名 | PascalCase | OrderListItem.vue | orderListItem.vue |
| composable | use 前缀 | useOrderList | orderListHook |
| 类型 / 接口 | PascalCase,不加 I 前缀 | UserInfo | IUserInfo |
- 表达意图而非实现,避免 `data`、`info`、`temp`、`res` 等模糊命名
- 使用业界标准用词(像素差异 `deltaPixel` 而非自创的 `spacePixel`)
- 避免自创缩写,使用完整拼写
- 函数命名必须动词开头
- 禁止魔法数字和硬编码字符串
- 同一概念全项目统一用词

**维度八:可维护性与工程规范**
* 函数职责:单个函数只做一件事,超过 50 行考虑拆分
* 代码重复:**注意区分"重复代码"和"重复知识"**——视觉上相同的两段代码若表达不同业务概念(如支付状态码 vs 订单状态码),不应强行合并(YAGNI > DRY,错误抽象比重复更昂贵)
* 注释:解释"为什么"而非"是什么";复杂业务逻辑、绕开框架限制的 hack、临时方案需注释
* 工程卫生:无 `console.log`、`debugger`、注释掉的代码块、未使用的 import

**维度九:样式**
**通用样式规范**
- 使用 `scoped` 或 CSS Module 避免污染
- 避免不必要的内联样式
- 颜色、间距、圆角、阴影等引用设计 token 而非硬编码
**原子化 CSS 规范(Tailwind / UnoCSS 通用)**
- **使用主题 token 而非任意值**:优先 text-gray-600、p-4、gap-2,避免任意值语法 text-[#6b7280]、p-[17px]、gap-[9px]。仅在设计稿确实是非标准值且确认不可纳入主题时才使用任意值,并加注释说明
- **禁止动态拼接类名(🔴 真 bug)**:text-${color}-500、p-${size} 在 Tailwind JIT 和 UnoCSS 默认扫描下**不会被识别**,生产构建后样式直接丢失。
- **推荐 variant-group 写法**:相同前缀的变体应合并,提升可读性并减少冗余
  ```html
  <!-- ❌ 重复前缀,扫读困难 -->
  <button class="hover:bg-blue-600 hover:text-white hover:shadow-md focus:bg-blue-600 focus:text-white">

  <!-- ✅ variant-group 合并,意图清晰 -->
  <button class="hover:(bg-blue-600 text-white shadow-md) focus:(bg-blue-600 text-white)">
  ```

**维度十:无障碍与国际化(如适用)**
- 图片 alt、交互元素键盘可达、表单 `<label>` 关联、`aria-*` 属性
- 硬编码文案是否接入 i18n

# 校准与禁止事项
**DO**
- 按实际严重程度分级，红色留给真正的红色问题
- 给出具体的文件:行号，而非模糊指向
- 解释**为什么**这是个问题，而非只说"这里不对"
- 承认亮点
- 给出明确的合并结论

**DON'T**
- 不要为了凑数量列"理论上可能"的问题
- 不要在没有真正读代码的情况下说"看起来不错"
- 不要把 **nitpick** 标成 🔴
- 不要给出像"改善错误处理"这样模糊的建议
- 不要回避明确的合并结论

**特殊情况**
- 如果代码整体质量很高，Issues 部分可以只有少量甚至空的等级
- 如果变更超过 500 行，按文件分组输出 Issues
- 如果某个审查维度在本次变更中不适用，跳过它，不要硬凑
