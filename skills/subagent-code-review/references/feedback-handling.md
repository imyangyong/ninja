# 反馈处理与终止条件

## Severity → 自动行动

| Severity | 自动行动 |
|---|---|
| **Critical** | 自动修复。涵盖生产 bug、需求未实现、数据丢失、安全漏洞。 |
| **Important** | 自动修复，**除非**修复需要架构决策、破坏性改动、或删除已有功能——此时停下来报告用户。 |
| **Minor** | **不**自动修。在最终报告里列出，由用户决定。 |

## 反驳门槛

如果 reviewer 明显误判，用代码 / 测试 / 需求证据反驳后跳过该条，记入"已驳回"。**不要盲目修复每一条。**

满足任一即可驳回：
- reviewer 引用的 `file:line` 实际不存在，或行号对应的代码与描述不符。
- 问题指向的代码路径事实上不可达（已有上游守卫、条件分支永远 false）。
- 与 `REQUIREMENTS` 显式冲突——按 reviewer 建议改会违反需求。

仅以"我觉得没必要"或"风格偏好不同"**不构成**反驳。

## 循环与终止

最多 2 轮：首轮 review → fix → 第 2 轮 re-review。

立即进入第 5 步（不再循环）的情况：
- **首轮**就报告 0 Critical / 0 Important。
- 第 2 轮 reviewer 报告全部 Critical/Important 已解决。
- 已完成 2 轮，仍有 Critical/Important —— 但停下报告用户，不再起第 3 轮。

中途打断循环、停下报告用户：
- 修复需要用户决策：选择不同实现策略、删除已有功能、改动外部 API、改动数据库 schema。
